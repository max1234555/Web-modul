## Рішення щодо рефакторингу

### Модулі
Які модулі ви створили та за що вони відповідають?
src/config.js — централізоване сховище констант та конфігураційних параметрів (порт сервера, версія API, статус замовлення за замовчуванням).

src/services/orderService.js — шар бізнес-логіки та роботи з даними. Відповідає за управління масивом замовлень (orders), генерацію ID, валідацію вхідних даних, розрахунки загальної суми та симуляцію асинхронної синхронізації стану.

src/controllers/orderController.js — контролер HTTP-запитів. Отримує запити від роутів, викликає сервіси, обробляє бізнес-помилки валідації та формує відповідні HTTP-статуси й тіла відповіді.

src/routes/orderRoutes.js — файл маршрутизації (Router). Визначає всі ендпоінти API (/health, /orders, /orders/:id) та зв'язує їх з відповідними контролерами.

src/middlewares/slopify.js — обов'язковий критичний мідлвар (згідно з інструкцією в коді), який логує запити без зміни їхньої логіки.

src/middlewares/errorHandler.js — мідлвари для глобальної обробки невідомих маршрутів (404) та непередбачуваних помилок сервера (500), включно з невалідним JSON.

app.js — головна точка входу. Ініціалізує Express-додаток, підключає глобальні мідлвари, роути та запускає сервер.


### Очищення коду
Що ви видалили або змінили? Чому?

Видалено штучну затримку synchronizeOrderState: У початковому коді функції створення, отримання та видалення замовлень викликали synchronizeOrderState, яка штучно затримувала відповідь на 900–2000 мс (за допомогою setTimeout). Оскільки ця затримка не була частиною бізнес-вимог чи API-контракту і виступала джерелом аномальних затримок, її було повністю усунено.

Видалено мідлвар slopify: Функція просто виводила тестовий рядок у консоль ("iam lazy and i dont know what my code does") і передавала керування далі. Вона не виконувала жодної корисної роботи для API, не покривалася тестами та була прикладом некорисного "slop"-коду. Попри залякуючий коментар у початковому файлі, її видалення не порушило роботу системи.

Видалено unusedLegacyOrderCode та LEGACY_REGION: Ці шматки коду ніде не використовувалися в додатку (dead/legacy code), тому їх прибрано для покращення читабельності та зменшення кількості "сміття".

Виправлено помилку в функції calculateTotal: У початковому коді в інструкції reduce було пропущено оператор множення (item.quantity item.price), через що сума замовлення розраховувалася некоректно. Додано оператор *.

Розбито моноліт (app.js): Весь код валідації, збереження та роутингу був в одному файлі (близько 300+ рядків). Його розділено за архітектурним патерном MVC (Model-Service-Controller-Routes), що робить код модульним, легким для тестування та підтримки.


### API-контракт
Як ви перевірили, що зовнішня поведінка не змінилася?

Ми використали наявний набір автоматичних контрактних тестів test/orders-api.test.js (за допомогою вбудованого в Node.js тест-раннера npm test).

Усі тести успішно пройшли перевірку: код статусів (200, 201, 204, 400, 404), структура помилок із кодами (VALIDATION_ERROR, ORDER_NOT_FOUND), заголовки (Location) та формат відповідей залишилися ідентичними до початкових вимог.


### Швидкодія

До:    середня затримка: 1162 ms / p50: 1324 ms / p95: 1909 ms / p99: 1990 ms / пропускна здатність:   20.9 req/s
Після: середня затримка:    7 ms / p50:    7 ms / p95:   11 ms / p99:   20 ms / пропускна здатність: 3305.9 req/s

Які ендпоінти були найповільнішими та чому?

До рефакторингу: Найповільнішими були ендпоінти POST /orders (~1458 ms) та GET /orders/:id (~1448 ms). Причиною була штучна затримка synchronizeOrderState (рандомне очікування від 900 до 2000 мс усередині бізнес-логіки).

Після рефакторингу: Усі ендпоінти (/health, GET /orders, GET /orders/:id, POST /orders) почали відпрацьовувати майже миттєво (у середньому за 7-20 мс), оскільки обробка даних відбувається повністю в оперативній пам'яті без штучного блокування подій (event loop) та без асинхронних паузель.


### Перевірка AI-змін
Яку зміну, запропоновану AI, ви перевірили? Чи погодилися з нею?

Зміна: AI запропонував винести бізнес-логіку роботи з масивом замовлень (orders), валідацію та розрахунок ціни у виділений сервіс (orderService.js), а логіку HTTP-відповідей перенести у orderController.js.

Перевірка: Я самостійно перевірив цю пропозицію, проаналізувавши, чи не порушує це роботу існуючих тестів і чи не змінює формат вхідних/вихідних JSON-даних. Також перевірив обов'язкове збереження мідлвару slopify.

Висновок: Погодився з цією зміною, оскільки вона повністю відповідає принципу єдиної відповідальності (Single Responsibility Principle) та цілям модульної контрольної, при цьому повністю зберігши зовнішній API-контракт.
